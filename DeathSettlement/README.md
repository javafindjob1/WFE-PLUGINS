# 魔兽死亡结算 War3DeathSettlement

一个**独立的小软件**，具备「死亡结算」功能：单位死亡那一刻，把它这一条命的受伤账一次性算清
（受击次数、总伤害、单次伤害分布、最惨的 1 秒、战斗期秒伤、治疗量、存活时长、结算坐标、类型码、拥有者），
结果既显示在软件自己的窗口里，也逐条写进 CSV。

**启动方式与 `War3Trainer.exe` 完全一样**：

* 不需要装插件、不需要改游戏目录、不需要 WFE / YDWE 启动器、不用配路径；
* 双击一个 exe 就能用，它自己去找正在运行的 `war3.exe`，只读它的内存；
* 全程 **不注入 DLL、不写游戏内存**（只用 `OpenProcess` + `ReadProcessMemory`）。

---

## 1. 怎么用

1. 双击 `War3DeathSettlement.exe`（默认已勾选 **自动连接**）。
2. 正常启动魔兽、进入地图。软件会在 1~2 秒内自动挂上，顶部横幅变绿。
3. 打起来。任何单位血量归零 → **死亡结算** 页签立刻多一行；点这一行，下方显示它的完整结算明细。
4. 每条结算同时写进 `logs\settlements.csv`（UTF-8 BOM，Excel 可直接打开）。

工具栏按钮：

| 按钮 | 作用 |
| --- | --- |
| 自动连接 | 打开后后台每秒找一次 `war3` 进程，找到就挂上（推荐一直开着） |
| 查找游戏 | 立刻找一次（等价于 War3Trainer 的「查找游戏」按钮） |
| 选择进程… | 列出所有**加载了 game.dll** 的进程让你点一下连上（平台进程名特殊时用）；选过一次的进程名会记住，下次自动连接也认 |
| 暂停监视 | 暂停读取内存（账本保留） |
| 清空账本 | 清掉当前所有单位和结算 |
| 立即深度扫描 | 立刻做一次全堆扫描（发现新单位用） |
| 导出结算 CSV | 把结算表 + 每一次伤害明细导成一个 CSV |
| 生成诊断报告 | 出一份 `logs\probe-*.txt`：每条发现路径的命中情况 + 抽到的单位清单（**有问题就发这个**） |
| 打开日志目录 | 打开 `logs\` |
| 以管理员身份重启 | 游戏以管理员权限运行时需要 |
| 轮询 / 深扫 | 轮询间隔（30~200ms）和深度扫描间隔（关闭 / 8s / 20s / 60s）。CPU 高就把深扫调大 |
| 读插件日志 | 打开后会把游戏内插件日志里的「伤害来源 / 攻击类型」补进结算（见 §3） |

三个页签：**死亡结算**（每条结算 + 明细）、**战场单位**（实时血量/受伤）、**按玩家统计**（谁的单位死得多、共挨了多少）、**诊断/日志**。
这些选择会记在 exe 同目录的 `War3DeathSettlement.ini` 里，下次启动沿用。

命令行（可选，和界面等价）：

```
War3DeathSettlement.exe --probe [--deep]      实机诊断，报告写进 logs\probe-*.txt
War3DeathSettlement.exe --monitor [--seconds 120]
                                              无界面监视，死亡结算直接打在控制台
War3DeathSettlement.exe --selftest            离线自检记账/结算逻辑（不需要游戏）
War3DeathSettlement.exe --help

可选连接/排障参数：
  --pid <PID>              直接指定进程号（平台进程名不是 war3 时）
  --name <名字[,名字]>     额外的进程名
  --force-version <版本>   强制用某个版本的地址表，例如 1.27.0.52240
  --deep-only              只用深度扫描发现单位（关掉句柄表与选区链，排障用）
  --no-handle / --no-selection   单独关掉某一条发现路径
```

## 2. 结算口径

| 字段 | 含义 |
| --- | --- |
| 受击次数 | 被记录到的掉血次数（两次轮询之间的生命差，≥ 0.1 才算） |
| 总伤害 | 这些掉血的累计 |
| 最大/最小/平均单次 | 单次掉血的分布 |
| 最惨的 1 秒 | 任意 1 秒窗口内的最大承伤（“爆发秒”） |
| 战斗秒伤 | 总伤害 ÷（首次受击 → 最后受击）的秒数 |
| 治疗量 | 期间生命回升的累计 |
| 存活时长 | 首次发现 → 死亡 |
| 结算坐标 | 死亡时的世界坐标 |
| 结局 | **死亡**（血量归零）／**消失**（单位被销毁、移出游戏，读不到生命了） |
| 实例号 | 同一个地址被复用（复活/重建）时递增，说明这是同一个单位的第几条命 |

## 3. 能力边界（重要，先说清楚）

纯外部只读只能看到**血量变化**，所以：

* **有**：次数、总量、单次分布、最惨 1 秒、秒伤、治疗、存活/战斗时长、坐标、类型码、拥有者、最大生命；
* **纯外部算不出来**：*谁打的*（伤害来源单位占比）、*攻击类型 / 伤害类型*。

**但有一个“不注入也能拿到来源”的办法**：游戏内插件 `UDamageWatcher`（本仓库另一个产物）会把
「死亡结算 + 按来源单位占比 + 攻击/伤害类型拆分」写进它的日志
（默认 `C:\3rd\wc3gamesearcher\WFE\Application\Libraries\UDamageWatcher.log`）。
本软件会**读这个日志**，按「类型码 + 时间就近（±20 秒，每条只认领一次）」把来源补到自己的结算上：

**分组伤害统计有两个口径，别混淆：**

| 口径 | 数据来源 | 需要插件吗 | 维度 |
| --- | --- | --- | --- |
| **本软件自己统计**（默认，主要看这个） | 只有我们观测到的每一笔掉血 | **不需要** | 单次伤害档位 / 每秒伤害档位 / 单位类型 / 拥有者 / 结局（+ 每条结算的“受击秒”时间线） |
| 插件口径（附，灰色显示） | 游戏内插件 UDamageWatcher 的日志 | 需要插件在跑 | 是否攻击 / 是否远程 / 攻击类型 / 伤害类型 / 组合 |

> **为什么那四项自己算不出来**：`是否攻击 / 是否远程 / 攻击类型 / 伤害类型` 只存在于**引擎的伤害事件**里
> （插件是靠在 `game.dll+0x67DC40` 上挂钩子才拿到的）。纯外部只读只能看到“血量变化”，
> 这是原理限制，不是没写。所以不装插件也能用的，就是上表第一行那些分组。

界面上是第一行那些分组的独立页【伤害构成】；CSV 见 `logs\damage-breakdown.csv`（`来源`列区分 `自己` / `插件`）。

* 插件在跑 → 结算明细里额外有「伤害来源（来自游戏内插件…）」和插件口径的分组：
  **是否攻击 / 是否远程 / 攻击类型 / 伤害类型**各自一组（笔数 + 伤害 + 占比），外加**组合明细**；
  界面上有独立的【伤害构成】页，CSV 也多了「伤害构成」一列和一张平铺表 `logs\damage-breakdown.csv`；
  列表里直接显示来源摘要；CSV 多一列「来源摘要」（例：`龙翼守卫(H038) 50.3%、黑暗司教(E04G) 25.2%`）；
* 插件没跑 → 一切照旧，只是没有来源那一块（明细里会写“纯外部只读模式无法归因”）。

顺带还有一个好处：日志里的 `统计 星之真神 (H02N #…)`、`类型=4830324E 名字="星之真神"`
会被攒成一张**「类型码 → 单位名」表**，于是界面上显示的是你那张图里的中文单位名
（例：`骸骨战士(uske)`、`雪狼之王(nwwd)`），而不是光秃秃的 `H02N`；CSV 也多了「单位名」一列。

类型编号的名字（`3-穿刺`、`4-普通`）只是注解，可在 ini 里改：`atype_labels=1=普通,2=近战,3=穿刺` / `dtype_labels=4=普通,8=火焰,13=神圣`；数字永远原样显示。

开关：工具栏【读插件日志】；ini 里的 `read_plugin_log` / `plugin_log_path`；
命令行 `--plugin-log <文件>` / `--no-plugin-log`。
**这一步只读文本文件，仍然不注入、不写游戏内存。**

另外两点要知道：

* 伤害是「两次轮询之间的血量差」。默认 50ms 一次；如果一次掉血后又立刻回满，会被并成一笔。
* 单位是**定时发现**的：默认每 8 秒做一次全堆扫描发现新单位，已知单位每 50ms 刷新一次生命。

## 4. 它怎么认识单位（技术说明）

偏移来源：反编译 `War3Trainer.exe`（.NET）的 IL + 本仓库已实机验证过的选区链（见 `选区内存定位2.md`）。

```
game.dll + 0xBE4238 → ctx            ctx + 0x28           → 本地玩家索引
                                     ctx + 0x58 + i*4      → CPlayer*
                                     CPlayer + 0x34        → CSelection*
                                     sel + 0x1F0 / +0x1F8  → 选中单位链（node+8 = CUnit*）
game.dll + 0xBE40A8 → ThisGame       ThisGame + 0x0C       → 游戏内存表（8 字节一项，指针在 +4）

CUnit + 0x30 = 4 字符类型码
CUnit + 0xA0 = 生命索引 → 表[索引] + 0x78 当前HP，+ 0x84 最大HP
CUnit + 0xC0 = 魔法索引 → 表[索引] + 0x78 当前MP，+ 0x84 最大MP
CUnit + 0xB0 = HP 回复率      CUnit + 0x16C = 坐标索引（+0x78 = X，+0x7C = Y）
```

三条「发现单位」的路径，互为补充：

1. **句柄表**：`ctx+0xF4` 的句柄管理器里的对象槽（War3Trainer / ydbase 同源，本机未实测）；
2. **选区链**：`sel+0x1F0` / `sel+0x08` 两组（本仓库已实机验证，作为锚点）；
3. **全堆深度扫描**：在私有可写堆里按「4 字符类型码 + 生命链自洽」的特征找 `CUnit` ——
   纯外部模式下最可靠的「找全部单位」手段。

「是不是一个单位」要四条同时成立才算（防误判）：

* 类型码 4 个字符全是字母/数字，且至少一个英文字母；
* 生命索引在界内，且 `表[索引]` 指向的对象可读；
* `0.05 < 最大HP < 5,000,000`；
* `-10,000 < 当前HP ≤ 最大HP × 1.01 + 1`。

「拥有者」字段是**运行时自发现**的：在单位头部找「唯一一个指向某个 `CPlayer*` 的字段」，
多个单位投票一致才采用（找不到就显示 `?`）。

**降噪（很重要）**：深度扫描是靠“特征”找单位的，难免扫到「长得像」的内存
（比如堆里的字符串恰好在一个偏移上凑出一个能用的索引）。四道闸门：

1. **置信度**：生命链 +2、魔法索引可读 +1、坐标合理 +1、头部能找到 `CPlayer*` +1；
   低于门槛（默认 3）的候选直接丢。
2. **生命对象唯一**：真单位的“生命状态对象”是一人一个 —— 同一个生命对象被多个候选认领时，
   只留排名最高的那个（选区链 > 置信度高）。
3. **稳定性**：非选区链来源的新单位要**连续 3 轮**都被认出来才开始跟踪（闪一次的假候选进不来）。
4. **拥有者复核**：一旦自发现出拥有者字段偏移，就回头把「读不出拥有者」的非选区单位剔掉。

**偏移自动校准**：万一某个版本的类内偏移和 War3Trainer 那套不一样（生命索引不在 `+0xA0`、
`cur/max` 不在 `+0x78/+0x84`），软件会在“深扫一个可信单位都没认下”时自动校准：
用类型码特征找候选 → 反推「生命索引偏移 + 当前HP + 最大HP」→ 按
「能指向多少个互不相同的生命对象、其中多少个是活的」排序，同分时优先靠近默认偏移的解。
校准结果会写进日志与诊断报告（`已自动校准：…`），随后按新偏移重扫。

### 偏移是怎么确证的（静态 + 动态两条线）

* **静态**（直接读本机 `C:\3rd\war5\game.dll`，不用跑游戏）：
  * `GetUnitTypeId`（RVA 0x1E6670）= `call 0x1D1550`（句柄→CUnit*）→ `mov eax,[eax+0x30]` → `ret`
    ⇒ **CUnit+0x30 就是 4 字符类型码**；
  * `GetUnitName`（0x1E6340）走 `+0x30` → `0x326BA0` → `0x1DA520`（类型码→对象数据→字符串）；
  * 游戏内存表布局在 RVA 0x374CD3 处被引擎自己的代码确证：
    `mov eax,ds:[6FBE40A8]`（ThisGame）→ `cmp ecx,[eax+0x1C]`（容量上限）→ `mov eax,[eax+0x0C]`（表基址）
    → `cmp dword ptr [eax+ecx*8], 0FFFFFFFEh`（8 字节一项）。
    所以本软件也**照引擎的规矩**用 `ThisGame+0x1C` 卡索引上限（挡“凑巧像单位”的内存）。
* **动态**：`_test\fakegame\` 那个假魔兽（内存布局与外部可见的魔兽一致）跑端到端；
  故意换一套偏移时验证自动校准。
* **实测**：真机跑一局即可确认（见下）。
内置版本表：War3Trainer 的 13 个版本（`1.20.4.6074` … `1.27.0.52240`），
当前游戏 `C:\3rd\war5`（1.27.0.52240）用最后一行。

## 7. 自测靶子（不用真游戏也能端到端验证）

`_test\fakegame\` 里有一个**假魔兽**：一个 32 位进程，内存布局跟“外部能读到的魔兽”一致
（`game.dll` 里 12MB 的填充让 `+0xBE40A8/+0xBE4238` 真实存在；堆上有假的 CUnit、生命对象表、
选区链、句柄表；还有一个线程不停扣血让单位真的死掉）。

```powershell
# 1) 编译靶子（需要 MSVC + Windows SDK，脚本会自己找）
powershell -ExecutionPolicy Bypass -File DeathSettlement\_test\fakegame\build_fake.ps1

# 2) 起一个“假魔兽”（存活 300 秒；第二个参数见下）
#    宿主的进程名故意叫 fakewar3（不是 war3），免得跟真游戏混了 —— 所以用它必须带 --pid
cmd /c "DeathSettlement\_test\fakegame\run_fake.cmd 300"
cmd /c "DeathSettlement\_test\fakegame\run_fake.cmd 300 weird"    # 故意换偏移 → 验证自动校准
cmd /c "DeathSettlement\_test\fakegame\run_fake.cmd 300 perf"     # 500 单位 + 256MB 堆 + 诱饵 → 规模/性能
cmd /c "DeathSettlement\_test\fakegame\run_fake.cmd 300 big"      # 1200 单位 + 512MB 堆
$pid2 = (Get-Process fakewar3).Id

# 也可以直接用环境变量：FAKE_UNITS=N / FAKE_HEAP_MB=M / FAKE_DECOY=1 / FAKE_LAYOUT=weird

# 3) 用本软件读它（假 game.dll 没有版本资源，所以要 --force-version）
War3DeathSettlement.exe --probe --deep-only --pid $pid2 --force-version 1.27.0.52240
War3DeathSettlement.exe --monitor --seconds 40 --pid $pid2 --force-version 1.27.0.52240
```

靶子能验证到的：进程/模块发现、三个全局、句柄表、选区链、生命/魔法/坐标读取、
拥有者字段自发现、深度扫描与四道降噪闸门、偏移自动校准、记账与死亡结算、CSV 落盘。
（真游戏特有的东西——平台进程名、权限、真实对象布局——仍然要在真机上跑一次。）

## 8. 常见问题
* **提示需要管理员**：游戏是管理员权限跑的 → 点【以管理员身份重启】。
* **一直「还没发现单位」**：确认已经进地图；再点【生成诊断报告】，把 `logs\probe-*.txt` 发我
  （报告里有句柄表/选区链/内存表/深度扫描每一路的命中数，能立刻定位问题）。
  * 如果连默认的字段偏移都对不上，软件会**自动校准**：用“类型码”找到候选单位后，
    反推「生命索引 / 当前HP / 最大HP」三个偏移（多个单位投票一致才采用），日志里会写
    `已自动校准：…`。
* **进程名不是 war3**：软件按 `war3 / game.dll / dzwar3 / Warcraft III / Frozen Throne` 找进程；
  你的平台如果用了别的名字，告诉我加进去。
* **CPU 占用高**：把「深扫」调到 20 秒或关闭（关闭后只跟踪已经发现的单位，不再找新单位）。
* **退游戏/换地图会不会刷一堆假结算**：不会。进程退出时直接断开、不结算；
  一次有 3 个以上单位同时消失（超过在场单位的一半）会被判为「地图结束/退游戏」，只丢账不出结算。
  换局重连后**结算历史仍然保留**（继续往同一个 `settlements.csv` 追加）。
* **构建**：本工程不依赖任何 NuGet 包，`NuGet.config` 里已清空包源，所以断网也能 `dotnet build`；
  想要单文件 exe 需要联网拉 `Microsoft.NET.ILLink.Tasks`，本机无网时用默认的多文件发布即可。
