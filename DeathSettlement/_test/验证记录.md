## 1.5 插件日志联动（补上“伤害来源/攻击类型”）

纯外部只能按血量差算伤害，拿不到“谁打的”。游戏内插件 `UDamageWatcher` 会把
「死亡结算 + 按来源单位占比 + 攻击/伤害类型拆分」写进
`C:\3rd\wc3gamesearcher\WFE\Application\Libraries\UDamageWatcher.log`；
本软件读这个文件，按「类型码 + 时间就近（±20s，每条只认领一次）」把来源补到自己的结算上。

端到端验证（假游戏 + 合成 GBK 日志）：

```
插件日志：解析 2 条，已补来源 2 条
[23:59:41] 来源已补：opeo ← 测试苦工(opeo) 测试恶魔(n000) 100%
CSV： hfoo | 消失 | 测试法师(Hpal) 50%、测试弓手(ewsp) 50%
     opeo | 死亡 | 测试恶魔(n000) 100%
```

### 这一段踩到的坑（都已修）

* **.NET 9 没有代码页 936**：`Encoding.GetEncoding(936)` 直接抛异常，补它要装 NuGet 包
  `System.Text.Encoding.CodePages`（本机无外网）。改成 P/Invoke `MultiByteToWideChar(936,…)`
  （`Core/Gbk.cs`），中文单位名照常解析。
* 拆分行正则写成 `^\d`，而日志里是**缩进**的 → 一个拆分行都匹配不上。
* 遇到不认识的行就 `Close()` 收尾，而表头后面紧跟的恰恰是那些行 → **整块被扔掉**（解析出 0 条）。
  改成「下一个表头 / 时间跳变 >3 秒 / 文本结束」才收尾。
* CSV 在结算那一刻就写，而来源 1~2 秒后才补上 → 新增的「来源摘要」列会永远是空的。
  改成“历史行读进内存 + 每次重写（表头+历史+本次会话全部结算）”，来源补上后同一行被补全。

### 顺带：单位中文名

## 1.7 静态验证：直接拿真实 `game.dll` 核对偏移（不需要跑游戏）

本机 `C:\3rd\war5\game.dll`（13,187,048 字节，1.27.0.52240）。
native 名表给出实现 RVA（`_tools\native_table_1.27.0.52240.txt`），
按 PE 段表换算文件偏移（`.text` VA=0x1000 / Raw=0x400 ⇒ 文件偏移 = RVA − 0xC00），
再逐字节反汇编：

**① `GetUnitTypeId`（RVA 0x1E6670）—— 直接确认 `CUnit+0x30` 是 4 字符类型码**

```
55 8B EC          push ebp ; mov ebp,esp
8B 4D 08          mov  ecx,[ebp+8]        ; Hunit 句柄
E8 D5 AE FE FF    call 0x1D1550           ; ← 句柄 -> CUnit*（我们文档里同一个 RVA）
85 C0 75 02 5D C3 test eax,eax ; jnz ; pop ebp ; ret
8B 40 30          mov  eax,[eax+0x30]     ; ★ CUnit+0x30 = 类型码
5D C3             pop  ebp ; ret
```

**② `GetUnitName`（RVA 0x1E6340）**：同样 `call 0x1D1550` → `8B 48 30`（读 `+0x30`）
→ `call 0x326BA0`（类型码→对象数据）→ `jmp 0x1DA520`（字符串 id→char*），
与仓库文档里的取名字链逐条一致。

**③ `GetUnitState`（RVA 0x1E6600）**：`jmp dword ptr [eax*4 + 0x6F669BBC]` 按 state 分派，
0/1 号走 `call [edx+0x12C] / [edx+0x130]` 虚函数（生命/最大生命），
和“生命不在 CUnit 里、而在按索引查的状态对象里”这件事吻合（所以必须走索引+表）。

**④ 游戏内存表布局（RVA 0x374CD3）—— 顺手挖到一个引擎自带的校验**

```
A1 A8 40 BE 6F    mov  eax, ds:[6FBE40A8]                 ; ★ ThisGame（我们的全局）
3B 48 1C          cmp  ecx, [eax+0x1C]                    ; ★ 索引上限 = ThisGame+0x1C
73 09             jae  skip
8B 40 0C          mov  eax, [eax+0x0C]                    ; ★ 表基址 = *(ThisGame+0x0C)
83 3C C8 FE       cmp  dword ptr [eax + ecx*8], 0FFFFFFFEh ; ★ 8 字节一项
```

⇒ 8 字节 stride / 指针在 +4 / 容量在 `ThisGame+0x1C` 全部由真实二进制确证。
于是给扫描器加了一条**引擎同款**的索引上限校验（`idx >= ThisGame+0x1C` 直接丢），
能挡掉一大批“凑巧像单位”的内存；靶子（标准布局与故意错位布局）复测仍 60/60 正常。

**⑤ 两个全局本身**：`0xBE4238` / `0xBE40A8` 都落在 `.data` 段内；
代码里 `mov ecx,ds:[6FBE4238]` 出现 880 次、`mov eax,ds:[6FBE4238]` 186 次，
`mov ecx,ds:[6FBE40A8]` 36 次、`mov eax,ds:[6FBE40A8]` 21 次 —— 是货真价实的引擎全局。

## 1.8 真·game.dll 的“挂载层”验证（在真进程里加载真 game.dll，不开游戏）

`_test\realattach\` 里有个 9 KB 的小宿主：`LoadLibrary("C:\3rd\war5\game.dll")` 然后挂着。
注意必须把工作目录设成游戏目录（否则依赖 DLL 找不到，LoadLibrary 会返回 126）。

| 验的东西 | 结果 |

| 从**真实** game.dll 读版本并与 13 版本表对上 | ✅ `1.27.0.52240`（假靶子没有版本资源，这条只有真 DLL 能验） |
| 读 `game.dll+0xBE4238` / `+0xBE40A8` 两个全局 | ✅ 都能读，未开局时值为 0 → 正确报“还没进地图” |
| base+RVA 寻址对不对（拿一个**已知结构**交叉验证） | ✅ 在活模块里读 `base+0x1E9A50`，其中 `+0x0C` 的 dword = `base+0x1DF360`，与 `native_table_1.27.0.52240.txt` 里第 0 条 `Deg2Rad` 的 `RVA=0x001DF360` **完全一致**（加载器重定位也正确） |
| 基址处 `MZ` 头 | ✅ 0x00905A4D |

### 这一节顺手修的两个真问题

1. **“读失败”被当成“读到 0”**：`Refresh()` 原来用 `Mem.U32()`（失败也返回 0），于是
   权限不足/进程刚退出会被误报成“游戏还没进地图”。改成用 `ReadU32(out)` 区分两种情况，
   读失败时明确提示“读不到引擎全局 —— 常见原因：游戏以管理员运行而本软件没有”。
2. **失败原因被一律写成“版本不支持”**：附着一个版本受支持、但还没进地图的进程时，
   `State` 却报 `UnsupportedVersion`（诊断报告里的“状态:”栏会误导人）。
   改成记住真正的失败状态 → 现在正确显示 `NotInGame`。

## 1.9 真机排查：「War3Trainer 看得到、我们看不到」的真相

现象：用户机器上 `War3Trainer.exe` 显示 `检测到游戏（3312）`，而我们的工具说「进程 3312 已经不在了」。

实测结论（三条，都是量出来的）：

1. **我（沙箱里的会话）看不到全机器进程**：`Get-Process` 只有 11~12 个，`tasklist`/CIM 直接 Access denied；
   而策略放开后同一个 shell 能看到 251 个。**更关键**：由这个 shell 启动的子进程（包括我们的 exe，
   哪怕通过 WMI 创建）**仍然只有 12 个进程的视野** —— 所以"我替你启动的那份"注定看不到你的游戏。
   用户截图里那个窗口正是这么起的（日志首行 `启动 2026-10-17 00:24:38` 就是我那轮截屏用的实例）。
2. **游戏进程拒绝一切访问**：同一用户、同一会话（session 1）下，
   我打开 `explorer.exe / cmd.exe / node / 自己` 全部成功，唯独 `War3.exe (3312)` 所有权限位都 `err=5（拒绝访问）`
   （连 `PROCESS_QUERY_LIMITED_INFORMATION` 都拒绝）。说明它是**提权/受保护**运行的 ——
   这也正是 `War3Trainer` 必须"以管理员身份运行"的原因。
3. 所以**读它必须提权**；我这边弹不出 UAC（`consent.exe` 不出现，`Start-Process -Verb RunAs` 直接挂住），
   真机读取只能由用户以管理员身份运行本软件来完成。

顺带用子代理把 `War3Trainer` 的查找逻辑逆向清楚了（报告：`_test\war3trainer_findgame_report.md`）：
入口是 `FrmMain::FindGame`，只在按钮和窗体 Load 触发，**全程序无 Timer/轮询**；
名字只有 `war3 / dzwar3`，模块 `game.dll`，用 `GetProcessesByName` 且**只取 `Process[0]`**；
成功后**永不重新校验**，所以它那个「检测到游戏(旧PID)」会一直挂着 —— 面板上的数字会停在最后一次读到的值。

### 据此补的 4 个洞（都是"它行、我们不行"的地方）

| 编号 | 问题 | 改法 |
| --- | --- | --- |
| G1 | 它只用 `FileVersion`，我们优先 `ProductVersion`；平台改造版两者可能不一致 | `ReadModuleVersions()`：`FileVersion → ProductVersion → FileX.X.X.X → ProductX.X.X.X` 逐个试，且 `game.dll` 与主模块两条路径都试 |
| G2 | `ReadModuleVersion` 先 `File.Exists`，路径超 260 或被 DACL 挡住就直接放弃 | 去掉硬门槛，直接 try `GetVersionInfo` |
| G3 | 我们要求 `Refresh()` 到 Ready 才算成功；"连上了但没进图"被当成"没找到"，且该路径句柄泄漏 | 保留 `bestNotReady` 会话并返回；其余候选 `Dispose` |
| G4 | 平台宿主 exe 名字不含 war3/warcraft 时自动路径抓不到 | `FindCandidates` 名字命中为 0 时按「谁加载了 game.dll」兜底扫描（15 秒节流 + 日志记录） |

回归：66/66 自检通过；真 `game.dll` 宿主仍能识别 `1.27.0.52240` 并正确报 `NotInGame`。

## 1.10 真机报告到手：核心链路全部成立 + 抓出两个真 bug

用户用**管理员权限**跑 GUI，对真实游戏（kkduizhan 平台的 1.27.0.52240）生成了界面诊断：

```
game.dll 基址: 0x7BF50000  大小 13152KB  路径 C:\Program Files (x86)\kkduizhan\config\gpatch\game\1.27.0\Game.dll
版本: 1.27.0.52240
ctx = 0x0F9200D8   ThisGame = 0x177500D0   GameMemory = 0x4BD20010   表容量 = 187827
本地玩家索引 = 0 ；CPlayer[0..15] 全部读出
选区链：CPlayer 0x1EE82BFC → sel → 节点 → 单位 0x1F0A9284 类型=J40E HP=16386/16686
```

⇒ 连接、版本识别、三个全局、玩家数组、选区链、生命链（`+0xA0`→表→`+0x78/+0x84`）、坐标**全部成立**。
（注意 game.dll 是**平台打过补丁的那份**，不在 `C:\3rd\war5` —— 版本识别依然命中，说明平台版也能用。）

### bug 1：4 字符类型码读反了（影响显示 + 插件日志匹配）

* 真机内存 `+0x30` = `4A 34 30 45`（"J40E"）；War3Trainer 同单位显示 `E04J`，插件日志里也是 `H02N / E04G` 这种写法。
* 原来按内存顺序拼串 ⇒ 我们显示 `J40E`、并且**按类型码匹配插件日志永远匹配不上**（来源/中文名全丢）。
* 修法：`TypeCodeFromBytes()` 反序。靶子也跟着改成"反着写"（`WriteTypeCode`），否则这个 bug 会被靶子掩盖 —— 这正是它藏到现在的原因。
* 复测：靶子单位显示 `hfoo / Hpal / ewsp`（不再反），实时结算里 `来源已补：hfoo ← 测试步兵(hfoo) 测试法师(Hpal) 50%`。

### bug 2：深度扫描的降噪把真机候选全丢了

真机报告里：`降噪：同一生命对象重复 2513 个、置信度不足 1266 个（已丢弃）`，最终只剩 1 个（来自选区链）。
也就是说深度扫描**找到了一大堆"像单位"的堆内存**，却没留下真的那个。

修法：加一条**几乎免费但极强**的判据 —— 真 CUnit 的 `+0x00` 是 game.dll 里的虚表指针：

* 真机证据：头部 `04 A7 99 7C` = 0x7C99A704，而 game.dll 基址 0x7BF50000、映像 ~13 MB ⇒ 正落在 game.dll 内；
* 实现：`VtableOk`（+2 分）＋深度扫描**必须**过这一关（选区链/句柄表等权威路径不强制）；
* 诊断里新增"虚表不像 game.dll 的 N 个"。

复测（靶子，也补上了虚表指针）：标准布局 **24/24**、错位布局校准后 **24/24**，字段偏移/拥有者照常自发现。

## 2. 靶子端到端（真实 32 位进程，内存布局与外部可见的魔兽一致）

靶子做的事：12 MB 模块填充让 `game.dll+0xBE40A8 / +0xBE4238` 真实存在；
堆上放假的 CUnit（类型码 `+0x30`、生命索引 `+0xA0`、拥有者 `+0x1C`）、
游戏内存表（8 字节一项、指针在 `+4`）、选区链、句柄表；另有线程扣血让单位真的死。

| 用例 | 期望 | 实测 |
| --- | --- | --- |
| 三条发现路径（句柄表 / 选区链 / 深度扫描） | 都能认出 12 个单位 | ✅ 每条都 12/12 |
| 生命、魔法、坐标、拥有者 | 值正确、拥有者自发现 `0x1C` | ✅ HP 186/280、坐标 (1024,512)、P1 |
| 深度扫描降噪 | 只留真单位，不出现堆里的 `HOME/SESS/PUBL` 之类 | ✅ 649 个特征命中 → 精确 12 个 |
| 故意错位布局（`FAKE_LAYOUT=weird`：索引 `+0xA4`、cur `+0x68`、max `+0x74`） | 自动校准找回来并重扫出单位 | ✅ 校准到 `0xA4/0x68/0x74`，12/12 |
| 死亡结算（`--monitor` 40~60 秒） | 出结算、数字合理、写 CSV | ✅ 9~12 条结算，含致命标记、最惨 1 秒、秒伤、明细 |
| 去重/稳定性/拥有者过滤 | 不再出现 `uske (?)` 这类“影子单位” | ✅ 每条结算的拥有者都是 P1 |

### 靶子测出来的真 bug（都已修）

1. `MaxDeepTotalBytes = 2400 << 20` **int 溢出成负数** → 深度扫描一个字节都不扫（工具在真机上会直接失灵）。
2. 深度扫描假阳性：堆里的字符串凑巧满足“类型码 + 生命链” → 加了置信度 + 生命对象唯一 + 稳定性 + 拥有者复核四道闸门。
3. 自动校准一开始选错偏移（票数被假候选刷高、`cur/max` 分不开、候选被截断漏掉真单位）→ 改成
   “指向多少个互不相同的生命对象 + 其中多少个是活的 + 同分靠默认偏移”。
4. 同一单位被认出多次 → 结算重复（`n000` 与 `npm_` 数字一模一样）。
5. 地址变化（对象搬迁/复活）会丢账 → 改成用**生命对象索引**当身份。
6. **单位挨着单位时拥有者永远发现不了**：自发现要读 `CUnit+0x800`，而单位只有 `0x400` 大，
   于是读进隔壁单位（隔壁也有拥有者指针）→ 每个单位都“2 个命中” → 投票恒空。
   500 单位自测里踩到；改成取**最小**命中偏移。
7. 界面：工具栏“游戏未运行”不刷新、一刀秒杀时秒伤算出 8000、右下明细框一直空、横幅提示不更新。
