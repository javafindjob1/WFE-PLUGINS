## 1.5 插件日志联动（补上“伤害来源/攻击类型”）

纯外部只能按血量差算伤害，拿不到“谁打的”。游戏内插件 `UDamageWatcher` 会把

`C:\3rd\wc3gamesearcher\WFE\Application\Libraries\UDamageWatcher.log`；
本软件读这个文件，按「类型码 + 时间就近（±20s，每条只认领一次）」把来源补到自己的结算上。

端到端验证（假游戏 + 合成 GBK 日志）：

CSV： hfoo | 消失 | 测试法师(Hpal) 50%、测试弓手(ewsp) 50%

### 这一段踩到的坑（都已修）

* **.NET 9 没有代码页 936**：`Encoding.GetEncoding(936)` 直接抛异常，补它要装 NuGet 包
  `System.Text.Encoding.CodePages`（本机无外网）。改成 P/Invoke `MultiByteToWideChar(936,…)`
  （`Core/Gbk.cs`），中文单位名照常解析。
* 拆分行正则写成 `^\d`，而日志里是**缩进**的 → 一个拆分行都匹配不上。
* 遇到不认识的行就 `Close()` 收尾，而表头后面紧跟的恰恰是那些行 → **整块被扔掉**（解析出 0 条）。
  改成「下一个表头 / 时间跳变 >3 秒 / 文本结束」才收尾。
* CSV 在结算那一刻就写，而来源 1~2 秒后才补上 → 新增的「来源摘要」列会永远是空的。
  改成“历史行读进内存 + 每次重写（表头+历史+本次会话全部结算）”，来源补上后同一行被补全。

## 1.7 静态验证：直接拿真实 `game.dll` 核对偏移（不需要跑游戏）

本机 `C:\3rd\war5\game.dll`（13,187,048 字节，1.27.0.52240）。
native 名表给出实现 RVA（`_tools\native_table_1.27.0.52240.txt`），
按 PE 段表换算文件偏移（`.text` VA=0x1000 / Raw=0x400 ⇒ 文件偏移 = RVA − 0xC00），
再逐字节反汇编：

**① `GetUnitTypeId`（RVA 0x1E6670）—— 直接确认 `CUnit+0x30` 是 4 字符类型码**

```
55 8B EC          push ebp ; mov ebp,esp
8B 4D 08          mov  ecx,[ebp+8]        ; Hunit 句柄
E8 D5 AE FE FF    call 0x1D1550           ; ← 句柄 -> CUnit*（我们文档里同一个 RVA）
85 C0 75 02 5D C3 test eax,eax ; jnz ; pop ebp ; ret
8B 40 30          mov  eax,[eax+0x30]     ; ★ CUnit+0x30 = 类型码
5D C3             pop  ebp ; ret
```

**② `GetUnitName`（RVA 0x1E6340）**：同样 `call 0x1D1550` → `8B 48 30`（读 `+0x30`）
→ `call 0x326BA0`（类型码→对象数据）→ `jmp 0x1DA520`（字符串 id→char*），
与仓库文档里的取名字链逐条一致。

**③ `GetUnitState`（RVA 0x1E6600）**：`jmp dword ptr [eax*4 + 0x6F669BBC]` 按 state 分派，
0/1 号走 `call [edx+0x12C] / [edx+0x130]` 虚函数（生命/最大生命），
和“生命不在 CUnit 里、而在按索引查的状态对象里”这件事吻合（所以必须走索引+表）。

**④ 游戏内存表布局（RVA 0x374CD3）—— 顺手挖到一个引擎自带的校验**

```
A1 A8 40 BE 6F    mov  eax, ds:[6FBE40A8]                 ; ★ ThisGame（我们的全局）
3B 48 1C          cmp  ecx, [eax+0x1C]                    ; ★ 索引上限 = ThisGame+0x1C
73 09             jae  skip
8B 40 0C          mov  eax, [eax+0x0C]                    ; ★ 表基址 = *(ThisGame+0x0C)
83 3C C8 FE       cmp  dword ptr [eax + ecx*8], 0FFFFFFFEh ; ★ 8 字节一项
```

⇒ 8 字节 stride / 指针在 +4 / 容量在 `ThisGame+0x1C` 全部由真实二进制确证。
于是给扫描器加了一条**引擎同款**的索引上限校验（`idx >= ThisGame+0x1C` 直接丢），
能挡掉一大批“凑巧像单位”的内存；靶子（标准布局与故意错位布局）复测仍 60/60 正常。

**⑤ 两个全局本身**：`0xBE4238` / `0xBE40A8` 都落在 `.data` 段内；
代码里 `mov ecx,ds:[6FBE4238]` 出现 880 次、`mov eax,ds:[6FBE4238]` 186 次，
`mov ecx,ds:[6FBE40A8]` 36 次、`mov eax,ds:[6FBE40A8]` 21 次 —— 是货真价实的引擎全局。

### 这一节顺手修的两个真问题

1. **“读失败”被当成“读到 0”**：`Refresh()` 原来用 `Mem.U32()`（失败也返回 0），于是
   权限不足/进程刚退出会被误报成“游戏还没进地图”。改成用 `ReadU32(out)` 区分两种情况，
   读失败时明确提示“读不到引擎全局 —— 常见原因：游戏以管理员运行而本软件没有”。
2. **失败原因被一律写成“版本不支持”**：附着一个版本受支持、但还没进地图的进程时，
   `State` 却报 `UnsupportedVersion`（诊断报告里的“状态:”栏会误导人）。
   改成记住真正的失败状态 → 现在正确显示 `NotInGame`。

## 1.9 真机排查：「War3Trainer 看得到、我们看不到」的真相

现象：用户机器上 `War3Trainer.exe` 显示 `检测到游戏（3312）`，而我们的工具说「进程 3312 已经不在了」。

实测结论（三条，都是量出来的）：

1. **我（沙箱里的会话）看不到全机器进程**：`Get-Process` 只有 11~12 个，`tasklist`/CIM 直接 Access denied；
   而策略放开后同一个 shell 能看到 251 个。**更关键**：由这个 shell 启动的子进程（包括我们的 exe，
   哪怕通过 WMI 创建）**仍然只有 12 个进程的视野** —— 所以"我替你启动的那份"注定看不到你的游戏。
   用户截图里那个窗口正是这么起的（日志首行 `启动 2026-10-17 00:24:38` 就是我那轮截屏用的实例）。
2. **游戏进程拒绝一切访问**：同一用户、同一会话（session 1）下，
   我打开 `explorer.exe / cmd.exe / node / 自己` 全部成功，唯独 `War3.exe (3312)` 所有权限位都 `err=5（拒绝访问）`
   （连 `PROCESS_QUERY_LIMITED_INFORMATION` 都拒绝）。说明它是**提权/受保护**运行的 ——
   这也正是 `War3Trainer` 必须"以管理员身份运行"的原因。
3. 所以**读它必须提权**；我这边弹不出 UAC（`consent.exe` 不出现，`Start-Process -Verb RunAs` 直接挂住），
   真机读取只能由用户以管理员身份运行本软件来完成。

顺带用子代理把 `War3Trainer` 的查找逻辑逆向清楚了（报告：`_test\war3trainer_findgame_report.md`）：
入口是 `FrmMain::FindGame`，只在按钮和窗体 Load 触发，**全程序无 Timer/轮询**；
名字只有 `war3 / dzwar3`，模块 `game.dll`，用 `GetProcessesByName` 且**只取 `Process[0]`**；
成功后**永不重新校验**，所以它那个「检测到游戏(旧PID)」会一直挂着 —— 面板上的数字会停在最后一次读到的值。

### 据此补的 4 个洞（都是"它行、我们不行"的地方）

| 编号 | 问题 | 改法 |
| --- | --- | --- |
| G1 | 它只用 `FileVersion`，我们优先 `ProductVersion`；平台改造版两者可能不一致 | `ReadModuleVersions()`：`FileVersion → ProductVersion → FileX.X.X.X → ProductX.X.X.X` 逐个试，且 `game.dll` 与主模块两条路径都试 |
| G2 | `ReadModuleVersion` 先 `File.Exists`，路径超 260 或被 DACL 挡住就直接放弃 | 去掉硬门槛，直接 try `GetVersionInfo` |
| G3 | 我们要求 `Refresh()` 到 Ready 才算成功；"连上了但没进图"被当成"没找到"，且该路径句柄泄漏 | 保留 `bestNotReady` 会话并返回；其余候选 `Dispose` |
| G4 | 平台宿主 exe 名字不含 war3/warcraft 时自动路径抓不到 | `FindCandidates` 名字命中为 0 时按「谁加载了 game.dll」兜底扫描（15 秒节流 + 日志记录） |

回归：66/66 自检通过；真 `game.dll` 宿主仍能识别 `1.27.0.52240` 并正确报 `NotInGame`。

### bug 2：深度扫描的降噪把真机候选全丢了

真机报告里：`降噪：同一生命对象重复 2513 个、置信度不足 1266 个（已丢弃）`，最终只剩 1 个（来自选区链）。

修法：加一条**几乎免费但极强**的判据 —— 真 CUnit 的 `+0x00` 是 game.dll 里的虚表指针：

## 1.11 伤害类型换算：以 YDWE 源码为准（我原来算错了）

用户指出“伤害类型里有个 3，不存在的类型”。查 `YDWE-master\Development\Plugin\Warcraft3\yd_jass_api\EventDamageData.cpp`
（第 79-89 行）看到权威实现：

```cpp
uint32_t damage_type()
{
    uint32_t v = data->damage_type;   // +0x14 的位掩码
    uint32_t n = 0;
    for (; v; v >>= 1) { ++n; }       // n = 位数
    return n - 1;                     // 对 1<<k 来说返回 k（bit 下标）
}
```

对 `1<<k`：循环 `k+1` 次 → 返回 **k**。我们原来写的是 `log2(mask) - 1`（多减了 1），
所以 `0x10` 被报成 **3**（应为 **4**）、`0x20` 被报成 4（应为 5）——用户看到的“3”就是这么来的。

修正后（自检锁定）：

| 掩码 | 旧（错） | 新（YDWE 口径） |
| --- | --- | --- |
| `0x10` | 3 | **4** |
| `0x20` | 4 | **5** |
| `0x4000` | 13 | **14** |
| `0x18`（多 bit） | 3 | **4**，显示为 `4(多类型0x18)` |

多 bit 掩码 YDWE 也是返回最高位（`floor(log2)`），我们照做并在界面加注原始掩码，不再假装是单一类型。

### 靶子测出来的真 bug（都已修）

1. `MaxDeepTotalBytes = 2400 << 20` **int 溢出成负数** → 深度扫描一个字节都不扫（工具在真机上会直接失灵）。
2. 深度扫描假阳性：堆里的字符串凑巧满足“类型码 + 生命链” → 加了置信度 + 生命对象唯一 + 稳定性 + 拥有者复核四道闸门。
3. 自动校准一开始选错偏移（票数被假候选刷高、`cur/max` 分不开、候选被截断漏掉真单位）→ 改成
   “指向多少个互不相同的生命对象 + 其中多少个是活的 + 同分靠默认偏移”。
4. 同一单位被认出多次 → 结算重复（`n000` 与 `npm_` 数字一模一样）。
5. 地址变化（对象搬迁/复活）会丢账 → 改成用**生命对象索引**当身份。
6. **单位挨着单位时拥有者永远发现不了**：自发现要读 `CUnit+0x800`，而单位只有 `0x400` 大，
   于是读进隔壁单位（隔壁也有拥有者指针）→ 每个单位都“2 个命中” → 投票恒空。
   500 单位自测里踩到；改成取**最小**命中偏移。
7. 界面：工具栏“游戏未运行”不刷新、一刀秒杀时秒伤算出 8000、右下明细框一直空、横幅提示不更新。

## 4. 2026-10-17 生命表“搬家”问题（平台联机/观战认不出单位）—— 已修 + 已复现验证

### 现象（真机）
平台联机/观战会话里 `ThisGame+0x0C` 读到 `0x3E4C0010` / `0x34E90010` / `0x3DEB0010`
这类地址，软件报“未映射/不可读” → 生命表基址找不到 → 全场单位“不像单位” → 战场单位/伤害构成空。
（`publish\logs\probe-20261017-150210/150741/151351.txt`、`dss-20261017-151035.log`）

### 根因
`RemoteProcess.IsReadable()` 查的是 **attach 那一刻** 的 VirtualQueryEx 快照。
引擎在进图/扩容/回收时会把生命表**重新分配**（旧表释放、新表在另一块内存），
这些新区域不在快照里 —— `ReadProcessMemory` 明明读得到，软件却判“未映射”。
于是真表被丢掉 → 自动校准在垃圾里挑了个“像表”的地址（15:06 那次甚至挑到 game.dll 映像里的
`0x799C2174`）→ 全场单位判死。这也解释了为什么“先进图、后开软件”常常正常。

### 修法
1. `IsReadable`：快路径查区域表 → 查不到**立刻重抓区域表**（节流 800ms）→ 还查不到就**直接读 4 字节实测**
   （每秒 2000 次预算，防深扫被假地址拖慢）；实测成功就顺手补新区域表。
2. 监视循环每 5 秒重抓一次区域表（否则深度扫描永远看不见新堆区）。
3. 换图判定改用 `(ctx, ThisGame)`；同一局里表基址变了只记
   `生命表基址变更：… → …（账本保留）`，**不再清账本**。
4. 校准加固：`anyStrong` 看**全部**已认出单位（以前只看“深度扫描”这一路，
   句柄表已认出 20 个单位还会误触校准，把错解 `0x1D8` 盖到正确偏移上）；
   采纳前先用新偏移试读候选，一个都认不出就回滚默认值。
5. `GameMemory` 解析顺序：**默认偏移 `ThisGame+0x0C` 优先**，校准值只在它读不出来时当备胎。

### 复现 + 验证（靶子新增 `FAKE_LATE_MS` / `FAKE_IMMORTAL` / `FAKE_NO_RESPAWN`）
靶子先 commit 一小块表并跑起来，**装好 N 毫秒后**把表搬到 64MB 预留区里另一块
（attach 时那块还是 MEM_RESERVE，旧表整块 decommit）—— 正好复刻“装好之后才分配的表”。

| 版本 | 表搬家后 |
| --- | --- |
| 旧版（15:08 发布） | 20 个单位**同时消失** → 误判“地图结束” → 校准到垃圾（`ThisGame+0x10C`）→ 单位 0 |
| 新版（1.0.1） | 单位 **20 → 20 不掉**，日志一条 `生命表基址变更：0x… → 0x…（账本保留）`，无校准、无清账 |

另外回归验证：普通死亡结算照常（20 秒出 5 条结算）；离线自检 **122/122**；
`--probe` 新增 §6（区域表状态 / 每次采样“区域表里有没有 vs 直接读成功吗”）、
§6.1（候选表 × 真单位打分）、§6.2（引擎读表指令原始字节 + 内存 .text 与磁盘文件逐字节比对）。

## 6. 2026-10-31 20:22 真机崩溃（按 Ctrl+Alt+R 之后约 6 秒）—— 已定位、已修、已复验

### 现象
20:22:46 按 Ctrl+Alt+R，日志正常写下「已记录 黑暗巨神兵(O01G)」；约 6 秒后 `War3.exe` 直接消失
（平台提示“游戏异常退出”）。ddh 日志停在 20:22:46.964，之后一个字都没写。

### 直接证据（WER + 崩溃转储）
* 事件日志：`War3.exe 1.27.0.52240`，故障模块 `ucrtbase.dll`，异常 `0xC0000409`，异常数据 `5`，
  偏移 `0x8AD52` = `_invoke_watson + 0x12`（参数 5 = `FAST_FAIL_INVALID_ARG`）。
* `%LOCALAPPDATA%\CrashDumps\War3.exe.21624.dmp` 的 EBP 链：
  `_invoke_watson` ← `__stdio_common_vsprintf_s + 0x1C0` ← `ddh.dll+0x15B43`（编译器的 `sprintf` 垫片）。
* 崩溃那一刻栈上的实参：格式串 `0x1001BF64` = `"%s(%s)"`、size = `0x40`（64）、
  目标缓冲 `0x7901DBD0` = `g_ddhGlobal[0].label`；该缓冲里正是一条**被截断的长中文名**
  `……【辅助单位】(e009`（62 字节 + 结束符，正好撞满 64）。

### 根因
`DdhUnitLabel()` 用 `sprintf_s(out, cap, "%s(%s)", name, codeTxt)` 拼“名字(码)”，而
`DdhGlobalAdd()` 传进来的标签只有 **64 字节**。UCRT 的 `sprintf_s`（`_s` 家族）放不下时
**不截断**，而是调无效参数处理器：`_invoke_watson` → `__fastfail(FAST_FAIL_INVALID_ARG)`，
整个 `War3.exe` 以 `0xC0000409` 当场终止。

⇒ **只要出现一个名字足够长的单位（这张图的 `……【辅助单位】`，名字约 70 字节），
它第一次挨打、被记进全局受击榜的那一刻，游戏必崩。** 和 Ctrl+Alt+R 只是时间相邻：
按 R 记录选中单位之后，下一次伤害事件里第一次见到这个长名字单位。

### 修法（`_test/hook/ddh.cpp`）
1. 新增 `DdhComposeLabel(name, codeTxt, out, cap)`：先按 **UTF-8 边界**把名字截到
   “放得下 `(码)` + 结束符”的长度（截断处补 `…`）再拼；`DdhUnitLabel()` 改为调它。
2. 全文件 `sprintf_s(` 统一换成 `DdhSprintf(...)` = `_snprintf_s(buf, cap, _TRUNCATE, ...)`：
   放不下只截断、**绝不**触发无效参数处理器（23 处调用一次性收口）。
3. `DdhSrcStat.label` / `DdhVictimStat.label` 由 64 → **96** 字节（`g_ddhTrack.label` 本来就是 96）。
4. 自检加第 8 组回归用例：长名字进 64 / 96 / 8 字节缓冲，截断后仍是合法 UTF-8、
   仍保留 `(码)` 后缀、空名空码写 `?`。

### 复验
* `cl /DDH_MSG_TEST ddh.cpp` → 自检**全部通过**（含新增断言）。64 字节用例输出 63 字节：
  `战×18 + … + (e009)`，末尾是 `E2 80 A6`，合法 UTF-8。
* 新 `ddh.dll` 的导入表里 **`__stdio_common_vsprintf_s` 已消失**（只剩 `vsnprintf_s`）——
  “放不下就崩”的那条路在二进制里已经不存在。
* 32 位进程里 `LoadLibraryW(ddh.dll)` 成功（`DllMain` 跑完、共享内存已建、可正常卸载）。
* 三处部署同步：`_test\hook\ddh.dll`、`publish\hook\ddh.dll`、`bin\Release\net9.0-windows\hook\ddh.dll`
  （同一 SHA256 前 12 位 `1F5853EE511B`，129024 字节）。

### 顺带
插件 `UDamageWatcherHook.cpp` 的 `ShowMessage()` 用的是 768 字节常驻缓冲，暂没这个风险；
但**任何往固定小缓冲里拼单位名的地方都必须走 `_TRUNCATE`**，否则同样会 0xC0000409。

## 8. 2026-11-01 「引擎伤害」回读：地图不注册伤害事件也能拿到（已实现 + 已部署）

### 探针实测（两轮真机，DDH_ENGINE_PROBE）

| 采样点 | 结果 |
| --- | --- |
| 伤害函数**入口**调 `GetEventDamage` 原实现 | 0.00（还没算） |
| 伤害函数**出口**调 `GetEventDamage` 原实现 | 0.00（事件已结束，守卫拦掉） |
| 出口读“当前事件对象 +0x30” | 多数是「无对象」（事件对象已出栈） |
| **出口读 `info+0x10`** | **= 引擎伤害** ✅ |

两例与地图真读到的值逐条吻合（都能用护甲公式对上）：

```
原始 5.00  → 出口 info+0x10 = 4.46  地图首值 = 4.46   （护甲 2 → 10.71% 减伤，5×0.89286 = 4.464）
原始 16.00 → 出口 info+0x10 = 14.29 地图首值 = 14.29 （同一护甲）
引擎探针[8]  depth=1 原始=5.00  入口+0x30=0.00 出口+0x30=0.00 对象+0x30=无对象 地图首值=4.46  取次=1 命中=+0x10
引擎探针[10] depth=1 原始=16.00 入口+0x30=0.00 出口+0x30=0.00 对象+0x30=无对象 地图首值=14.29 取次=1 命中=+0x10
```

⇒ 引擎在伤害函数内部把**护甲/加成之后的实际伤害**写回 `info+0x10`；出口再读一次就等于
`GetEventDamage` 本会返回的值。**不需要再加任何 hook。**

（个别 `取次=0` 的小伤害出口值会变大，例：1.00 → 1.50 / 2.00，应该是引擎自己的加成/易伤；
这类没有地面真值可对，探针日志里能看到。）

### 实现（`_test/hook/ddh.cpp`）

`DdhDamageFunc` 在原函数返回后再读一次 `info+0x10`，三个闸门都过才写回 `engineDamage/engineValid`：

1. 地图没读过：`g_engineFirstSet[level] == 0`；
2. 地图没改过：`g_setCalls[level] == 0`；
3. 结构体 `+0x00`（来源单位）仍是这次事件的来源 —— 防结构体被下一次事件复用。

写回时 `engineCalls` 保持 **0**（表示“ddh 回读”，不是地图读的）。

C# 侧配套（`Core/DamageHook.cs`）：
* `EngineValueValid => EngineValid` —— 回读值也显示，不再要求 `取次 > 0`；
* `MapRate`（倍数）仍要求 `EngineCalls > 0` —— 回读事件不显示倍数，
  否则会拿“血差 ÷ 引擎伤害”冒充“地图改动倍数”。

### 验证

* ddh 离线自检（`DDH_MSG_TEST`）全过；
* C# `--selftest` **305 / 305**；
* `ddh.dll` 132096 字节，SHA256 前 12 位 `F83FC9567FD7`，三处同步

* 新版 `War3DeathSettlement.dll/exe` 已复制到 `publish\`（重启软件生效）。

## 10. 2026-11-01 Dota 拿不到「引擎伤害」—— 地图只 SetEventDamage、从不 GetEventDamage
