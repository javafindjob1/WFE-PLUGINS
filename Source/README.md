# 魔兽死亡结算 War3DeathSettlement

本项目用于记录魔兽争霸中的逐笔伤害、按来源和类型聚合伤害，并在单位死亡后显示死亡结算。

> 本 README 位于正式源码目录 `Source`。以下构建、测试和发布命令均从本目录执行；
> 逆向脚本、地图提取数据和临时分析材料位于上级目录 `TempAnalysis`。

当前正式使用方式是：

* **WFE 附加库**：WFE 注入单个完整 `ddh.dll`，只负责伤害钩子、事件环和 SQLite 落库。
* **桌面程序**：`War3DeathSettlement.exe` 读取 SQLite 并显示死亡结算、伤害事件和战场单位。
* **游戏内只提供本地阵亡总结**：没有结算按钮、完整页面、WebView2 宿主或共享画面。

> 本文档前面的“当前版本总览”和交互逻辑优先于后面的历史实现说明。
> 旧 WinForms 页面、纯只读记账和早期游戏内面板仍保留作兼容或排障参考。

## 0. 当前版本总览（2026-11-20）

### 0.1 运行组件

| 组件 | 位置 | 职责 |
| --- | --- | --- |
| WFE | `C:\3rd\wc3gamesearcher\WFE` | 加载附加库，启动魔兽时注入 ddh |
| `ddh.dll` | WFE `Application\Libraries` | 单一采集模块：挂伤害钩子、维护事件环、写 SQLite |
| `War3DeathSettlement.exe` | `Desktop` | 桌面页面：读取 SQLite、筛选、分页和历史查看 |
| SQLite | `%LOCALAPPDATA%\War3DeathSettlement\ddh\ddh-events.db` | 保存会话、事件、结算和单位属性 |

### 0.2 从进图到显示结算的数据流

1. WFE 注入 `ddh.dll`，延迟 3 秒后在游戏进程内完成初始化并挂载钩子。
2. ddh 挂钩 `game.dll+0x67DC40` 伤害函数；入口记录原始伤害、来源和触发单位，出口读取最终伤害与前后血。
3. ddh 将事件写入内存事件环，同时批量写入 SQLite 的 `game_events`、`game_settlements`、`game_units`。
4. 桌面程序每 0.5 秒读取当前会话摘要；死亡结算页和伤害事件页都按页查询。
5. 所有筛选、分页、历史会话和诊断操作都在桌面程序中进行。
6. 游戏进程内不再创建结算按钮、画面纹理、页面宿主或共享画面通道。

### 0.3 对局会话与数据库

当前会话 ID 形如 `14F700D8-156000D0`，由 `ctx + ThisGame` 两个游戏状态值组成。

主要表：

| 表 | 内容 |
| --- | --- |
| `game_sessions` | 会话 ID、地图名、开始时间和更新时间 |
| `game_events` | 每一笔伤害事件 |
| `game_settlements` | 每个受害单位的死亡结算摘要 |
| `game_units` | 战场单位属性和名称/称谓缓存 |

已知限制：`ctx + ThisGame` 是内存地址组合，后续游戏可能复用相同值，导致旧会话数据混入新局。
后续应给会话增加一次性启动/地图 nonce，并在代次变化时清理旧 ID 数据。

### 0.4 伤害数值口径

| 指标 | 当前含义 |
| --- | --- |
| 原始伤害 | 伤害函数入口 `info+0x10` 的账面值，尚未完成护甲、类型和地图改写 |
| 引擎伤害 | 原伤害函数退出后 `info+0x10` 的值，已包含护甲、攻防类型等引擎计算 |
| 地图伤害 / 生效伤害 | 调用方 `*out` 的最终值，包含地图 `SetEventDamage` 改写 |
| 净掉血 | 伤害函数入口和出口读到的真实血量差；嵌套时扣除同目标子事件 |
| 倍数 | 地图伤害 ÷ 引擎伤害；`1×` 表示没有改写，击杀溢出时是实际钳制比例 |
| 本层前血→后血 | 本层伤害函数进出的真实血量读数 |
| 层 | 嵌套深度，1 是最外层；DOT、反伤、追加伤害通常产生更深层 |

最终伤害只要求出口 `*out` 和引擎伤害读取成功，不再要求本帧实际掉血。
因此允许出现“地图伤害 > 0、净掉血 = 0”：伤害发生了，但同一帧回血抵消了生命差。

如果目标无敌、免疫或护盾完全吸收，`净掉血` 可能是 0；最终 `*out` 是否可信仍要结合该行的
前后血、地图机制和日志判断。`?` 表示没有测到，`0.00` 表示测到了 0。

### 0.5 页面与交互逻辑

#### 顶部通用区域

- 页签：`死亡结算`、`伤害事件`、`战场单位`。
- 桌面程序显示筛选框；`死亡结算` 和 `伤害事件` 由 SQLite 统计总数并查询当前页。
- 桌面壳的 `战场单位` 页在浏览器内直接筛选当前快照。

#### 死亡结算

- 默认选中最新结算行；单击其它行后，下方从 SQLite 加载该结算的伤害构成。
- 默认最新结算在上，每页最多 200 条；触发单位点击筛选在 SQLite 中完成，可翻页查看当前会话的全部结算。
- 顶部搜索在 SQLite 中完成。
- 主表冻结“时间、触发单位”列；展示类型码、实例 ID、玩家、结局、实例号、受击数、
  总伤害、最大单次、最惨 1 秒、秒伤、存活时间和战斗时间。
- 伤害构成按来源和攻击/伤害类型组合聚合，显示笔数、原始伤害、引擎伤害、地图伤害、净掉血和占比。

#### 伤害事件

- 默认最新事件在上，每页最多 500 条。
- 固定前三列：**时间、触发单位、伤害来源**；横向滚动时这三列保持在左侧。
- 点击“触发单位”或“伤害来源”中的单位名称，按 **类型码 + 是否镜像** 筛选，
  不绑定单个对象地址；表头显示筛选标签和 `×`。
- 可以分别拖动“伤害来源”和“本层前血→后血”列的右边缘调整宽度。
- 桌面壳顶部搜索与列筛选按 AND 叠加。
- 只有位于第 1 页且垂直滚动位置 `< 50` 时，新事件到达后才自动刷新，避免查看旧页时列表跳动。
- 上一页、下一页按钮按筛选后的总页数工作。

#### 战场单位

- 显示伤害入口按 `CUnit*` 捕获并写入 SQLite 的最小/最大攻击力、攻击范围、
  护甲、攻击速度、攻击间隔和蝗虫；攻击频率由界面计算。
- 读取失败的字段显示为 `?`；移速、视野和三维仍不读取。
- 桌面壳中名称/称谓、类型码和地址可被顶部筛选匹配。
- 该页是只读属性页，没有点击行下钻。

#### 历史与桌面工具

- 桌面版顶部可打开“历史”，选择历史会话后进入只读历史模式。
- 历史模式下显示“回到实时”，点击后重新读取当前游戏会话。
- “日志”打开运行日志目录，“设置”打开配置文件。

#### 游戏内无界面

- 不显示结算按钮或完整页面；仅在本机英雄死亡后显示原生承伤总结图表。
- 不启动 `ddh_web`，不创建 `Local\DdhHtml_<游戏PID>` 画面通道。
- 鼠标、键盘和游戏渲染均由魔兽原生处理，插件只做只读伤害采集。

### 0.8 当前常见限制

- 会话 ID 可能被后续对局复用，造成旧结算残留。
- `game_events.victim_name/source_name` 经常为空；界面名称由 `game_units` 在查询后解析。
  因此按显示名称搜索事件可能找不到，类型码和地址更可靠。
- `game_units` 按“会话 + 类型码 + 镜像”去重，同一类型可能有多个事件地址但只保留一个单位属性实例。
- 回血、护盾、无敌和免疫可能使“地图伤害 > 0”与“净掉血 = 0”同时出现。
- `?` 表示未测量，不是 0；只有 `0.00` 才表示测量结果为零。
- 更新 `ddh.dll` 后必须完整重启 WFE，不能只重启魔兽。

## 1. 怎么用

**使用方式**：通过 WFE 启动魔兽并进入地图，ddh 在后台记录事件；打开
`War3DeathSettlement.exe` 查看结算。游戏内没有任何结算按钮或页面。

1. 双击 `War3DeathSettlement.exe`。
2. 正常启动魔兽、进入地图。软件会自己一直等/自动挂上（不用点按钮），顶部横幅变绿。
3. 打起来。任何单位血量归零 → **死亡结算** 页签立刻多一行；点这一行，下方显示它的完整结算明细。
4. **不落 CSV**：结果只在界面里看（日志仍然写 `logs\dss-*.log`）。

桌面版工具栏：

| 按钮 | 作用 |
| --- | --- |
| 查找游戏 | 立刻找一次 war3 进程（平时不用点，自动连接一直开着） |
| 历史 | 打开 SQLite 历史会话列表；选中后进入只读历史模式 |
| 回到实时 | 从历史模式返回当前游戏会话 |
| 日志 | 打开 `logs\` |
| 设置 | 打开配置文件 |

页签有三个：**死亡结算**、**伤害事件**、**战场单位**。启动后默认停在【死亡结算】。
死亡结算页包含结算列表、选中项的伤害构成和完整明细。
（原来的【伤害构成】已并进【死亡结算】：下半部分就是**所有结算的分组统计**（每条结算先一行Σ来源汇总、再铺组合明细）；原来右下角那块文字明细已按要求去掉。）

轮询间隔、读不读插件日志、伤害钩子开关等**只在 ini 里改**（exe 同目录 `War3DeathSettlement.ini`）：
`interval_ms` / `read_plugin_log` / `hook_enable`（伤害钩子默认 1 = 开）。

**马甲单位（带蝗虫技能 Aloc）自动识别，不按名字/类型码写死**：ddh 对每个伤害目标实测
`GetUnitAbilityLevel(handle, 'Aloc') > 0`（与 YDWE 同口径：`<= 0` = 普通单位），命中的不进死亡结算、
也不进分组统计。地址变了时按**实测到 Aloc 的类型码**兜底匹配（类型码是运行时学到的，不是写死的表）。

ini 的 `ignore_unit_names` 是**可选的手动名字忽略名单**（默认空，逗号/分号分隔），
被忽略的单位不进死亡结算（也不进历史文件和分组统计），也不参与后续跟踪；
它**不参与马甲判定**。环境变量 `DSS_IGNORE_UNIT_NAMES` 可临时覆盖（例如测试时只忽略 `hfoo`）。改完 ini 要**重启软件**才生效。

### 1.1 游戏内阵亡总结

- 本地英雄死亡后显示原生承伤总结：四类伤害、来源分段和 10 秒柱状图。
- 默认显示无文字缩版，只保留致命击杀者头像和细分伤害条；点击缩版任意位置展开，点击展开版右侧箭头收起。
- 缩版和展开版标题区显示致命击杀者头像；展开版标题区同时显示击杀者名称和“死亡前 10 秒”窗口。
- 展开版上半区为双栏：左右数值右对齐到彩条起点，伤害类型名称绘制在固定宽度条形轨道内；右栏显示前 6 个“英雄伤害”来源的头像、数值和分段条，其余来源合并为“其他”；柱状图横轴显示从左到右递增的游戏内时间 `MM:SS`。
- 图标属于按类型码索引的单位类型属性：伤害入口与其他战斗属性一起同步解析并缓存 BLP 路径，路径容量为 256 字节；阵亡总结只读缓存，不再次调用 `GetUnitData`。
- 统计在伤害回调内完成，面板只在 Hook 退出后由游戏线程创建。
- 不提供按钮、点击下钻、共享内存、WebHost 或 3D 头像。
- 删除 `~`、`Esc` 和调试热键对应的旧面板显示路径。
- 删除桌面端自动排队、英雄判定、旧面板协议推送和“游戏内预览”入口。
- 死亡数据仍会写入 SQLite，并继续显示在死亡结算、伤害事件和战场单位页面。

## 2. 结算口径

| 字段 | 含义 |
| --- | --- |
| 受击次数 | 被记录到的掉血次数（两次轮询之间的生命差，≥ 0.1 才算） |
| 总伤害 | 这些掉血的累计 |
| 最大/最小/平均单次 | 单次掉血的分布 |
| 最惨的 1 秒 | 任意 1 秒窗口内的最大承伤（“爆发秒”） |
| 战斗秒伤 | 总伤害 ÷（首次受击 → 最后受击）的秒数 |
| 治疗量 | 期间生命回升的累计 |
| 存活时长 | 首次发现 → 死亡 |
| 结算坐标 | 死亡时的世界坐标 |
| 结局 | **死亡**（血量归零）／**消失**（单位被销毁、移出游戏，读不到生命了） |
| 实例号 | 同一个地址被复用（复活/重建）时递增，说明这是同一个单位的第几条命 |

## 3. 能力边界（重要，先说清楚）

纯外部只读只能看到**血量变化**，所以：

* **有**：次数、总量、单次分布、最惨 1 秒、秒伤、治疗、存活/战斗时长、坐标、类型码、拥有者、最大生命；
* **纯外部算不出来**：*谁打的*（伤害来源单位占比）、*攻击类型 / 伤害类型*。

**但有一个“不注入也能拿到来源”的办法**：游戏内插件 `UDamageWatcher`（本仓库另一个产物）会把
「死亡结算 + 按来源单位占比 + 攻击/伤害类型拆分」写进它的日志
（默认 `C:\3rd\wc3gamesearcher\WFE\Application\Libraries\UDamageWatcher.log`）。
本软件会**读这个日志**，按「类型码 + 时间就近（±20 秒，每条只认领一次）」把来源补到自己的结算上：

**分组伤害统计有两个口径，别混淆：**

| 口径 | 数据来源 | 需要插件吗 | 维度 |
| --- | --- | --- | --- |
| **本软件自己统计**（默认，主要看这个） | 只有我们观测到的每一笔掉血 | **不需要** | 单次伤害档位 / 每秒伤害档位 / 单位类型 / 拥有者 / 结局（+ 每条结算的“受击秒”时间线） |
| 插件口径（附，灰色显示） | 游戏内插件 UDamageWatcher 的日志 | 需要插件在跑 | 是否攻击 / 是否远程 / 攻击类型 / 伤害类型 / 组合 |

> **为什么那四项自己算不出来**：`是否攻击 / 是否远程 / 攻击类型 / 伤害类型` 只存在于**引擎的伤害事件**里
> （插件是靠在 `game.dll+0x67DC40` 上挂钩子才拿到的）。纯外部只读只能看到“血量变化”，
> 这是原理限制，不是没写。所以不装插件也能用的，就是上表第一行那些分组。

这些分组显示在【死亡结算】页：选中一条结算，下左的「伤害构成」里就是它（四维用数字）。

* 插件在跑 → 结算明细里额外有「伤害来源（来自游戏内插件…）」和插件口径的分组：
  **是否攻击 / 是否远程 / 攻击类型 / 伤害类型**各自一组（笔数 + 伤害 + 占比），外加**组合明细**；
  【死亡结算】页下左的伤害构成里会显示钩子口径的组合行；
  列表里直接显示来源摘要（例：`龙翼守卫(H038) 50.3%、黑暗司教(E04G) 25.2%`）；
* 插件没跑 → 一切照旧，只是没有来源那一块（明细里会写“纯外部只读模式无法归因”）。

顺带还有一个好处：日志里的 `统计 星之真神 (H02N #…)`、`类型=4830324E 名字="星之真神"`
会被攒成一张**「类型码 → 单位名」表**，于是界面上显示的是你那张图里的中文单位名
（例：`骸骨战士(uske)`、`雪狼之王(nwwd)`），而不是光秃秃的 `H02N`。

类型编号的名字（`3-穿刺`、`4-普通`）只是注解，可在 ini 里改：`atype_labels=1=普通,2=近战,3=穿刺` / `dtype_labels=4=普通,8=火焰,13=神圣`；数字永远原样显示。

开关：ini 里的 `read_plugin_log` / `plugin_log_path`（界面上没有这个按钮了）；
命令行 `--plugin-log <文件>` / `--no-plugin-log`。
**这一步只读文本文件，仍然不注入、不写游戏内存。**

另外两点要知道：

* 伤害是「两次轮询之间的血量差」。默认 50ms 一次；如果一次掉血后又立刻回满，会被并成一笔。
* 已知单位每 50ms 刷新一次生命；新单位通过句柄表 / 选区链发现，伤害钩子事件里的
  来源/触发单位指针也会作为锚点补进账本（没被选中过的单位同样能被跟踪、结算）。

### 3.1 伤害事件页里的「伤害 / 实际伤害」

伤害钩子（**默认开**，ini 里 `hook_enable=1`）跑起来后，【伤害事件】页每一行是这样的：

| 列 | 含义 | 怎么来的 |
| --- | --- | --- |
| **时间** | 事件发生的时间 | 事件记录时的时间戳 |
| **触发单位** | 挨打的是谁 | 受伤单位 `+0x30` 类型码；当前 Vue 页面点击单位名称后按“类型码 + 镜像”筛选 |
| **伤害来源** | 打人的是谁 | 结构体 `+0x00` 的来源单位 → `+0x30` 类型码；当前 Vue 页面点击单位名称后按“类型码 + 镜像”筛选 |
| **攻击 / 远程 / 攻击类型 / 伤害类型** | 一行显示四项引擎事件属性，例如 `0 / 0 / 0 / 26` | 是否攻击 / 是否远程各为 `0/1`，后两项为引擎数字类型 |
| **层** | 这次事件在第几层，使用紧凑列宽 | 1 = 最外层；>1 = 地图在伤害事件里又触发了伤害（DOT/反伤/连环） |
| **原始伤害** | 引擎伤害结构体里的账面值 | ddh.dll 在伤害函数（`game.dll+0x67DC40`）**入口**抄的 `+0x10`（地图/引擎都还没动它） |
| **引擎伤害** | 原伤害函数退出后 `info+0x10` 的值（含护甲、攻防类型等引擎计算） | v20 在 `game.dll+0x67DC40` 出口回读，不再依赖地图调用 `GetEventDamage` |
| **地图伤害** | 调用方 `*out` 的最终生效值，包含地图 `SetEventDamage` 改写 | 出口 `*out` 与引擎伤害读取成功即可；不要求本帧实际掉血 |
| **净掉血** | 血差 | 原函数返回后前后两次读血相减（本层净值，嵌套扣内层） |
| **倍数** | **地图伤害 ÷ 引擎伤害** | 1 = 地图没改；>1 增伤；<1 减伤/护盾/免疫或击杀钳制 |
| **本层前血→后血** | 真实读数（前血 → 后血，嵌套时外层后血含内层） | 引擎直接读到的**真实前血 / 真实后血**；不再用 前血 − 净掉血 合成 |

（单位对象指针/地址不再单独占两列，页顶筛选就是按这两个类型码来。
明细表已删除「掩码」列；数据库里的 `damage_mask` 字段仍保留，只是不再显示。）
伤害事件页也不再显示“是否英雄”列；英雄标志仍保存在事件 `unit_flags` 中供后台逻辑使用。

要点：

* **全程不调 JASS、不改游戏代码**：只改栈上 4 个字节（返回地址）+ 读内存；
  安装时会先扫一遍函数体确认结尾是 `ret 0x10`，扫不到就**只记“伤害”、不碰返回地址**（宁缺勿错）。
* **读不到就是 `?`**：前血 ≤ 0（目标已死）、生命表读不到、对象失效，或出口 `*out` / 引擎伤害
  没有读取成功，都按“没测到”处理，不拿别的值冒充。
* **点击单位筛选**：点击“触发单位”或“伤害来源”中的单位名称，立即按“类型码 + 镜像”过滤；
  筛选标签中的 `×` 用于清除。顶部全局搜索和列筛选按 AND 叠加。
* **所有伤害都显示两位小数**（原始/引擎/地图/净掉血/汇总/秒伤/单次…）。
* **横向滚动固定列**：伤害事件表前三列“时间、触发单位、伤害来源”固定，便于持续核对单位和事件。
* 页顶【清除伤害明细】= 清空事件列表，并把各条结算里的伤害构成/来源汇总一起清掉（结算行本身保留）。
* **溢出不算全**：伤害 90000 但只剩 10000 血 → 净掉血 = 10000。
* **嵌套**：地图的 DOT/追加/反伤会在一次伤害里递归触发新的伤害事件。我们用和
  `UDamageWatcherHook.cpp` 完全一样的记账（深度 1..16，`own = 整段掉血 − 内层累计`），
  所以**内层记自己的、外层扣掉内层**，加起来不重不漏。
  注意：外层那一行的「进入→退出」实测窗口里含着内层掉血，所以「本层前血→后血」直接显示
  引擎读到的**真实前血 → 真实后血**（外层后血自然含内层掉血）。
* 与游戏内插件的差别：插件是“地图第一次 `GetEventDamage()` 的值 vs 事件内前后血”，
  ddh 是“函数入口结构体值 vs 函数返回后的血”。正常图里两者一致；差异场景见 §8 常见问题最后一条。

## 4. 它怎么认识单位（技术说明）

偏移来源：反编译 `War3Trainer.exe`（.NET）的 IL + 本仓库已实机验证过的选区链（见 `选区内存定位2.md`）。

```
game.dll + 0xBE4238 → ctx            ctx + 0x28           → 本地玩家索引
                                     ctx + 0x58 + i*4      → CPlayer*
                                     CPlayer + 0x34        → CSelection*
                                     sel + 0x1F0 / +0x1F8  → 选中单位链（node+8 = CUnit*）
game.dll + 0xBE40A8 → ThisGame       ThisGame + 0x0C       → 游戏内存表（8 字节一项，指针在 +4）

CUnit + 0x30 = 4 字符类型码
CUnit + 0xA0 = 生命索引 → 表[索引] + 0x78 当前HP，+ 0x84 最大HP
CUnit + 0xC0 = 魔法索引 → 表[索引] + 0x78 当前MP，+ 0x84 最大MP
CUnit + 0xB0 = HP 回复率      CUnit + 0x16C = 坐标索引（+0x78 = X，+0x7C = Y）
```

两条「发现单位」的路径，外加钩子事件锚点：

1. **句柄表**：`ctx+0xF4` 的句柄管理器里的对象槽（War3Trainer / ydbase 同源，本机未实测）；
2. **选区链**：`sel+0x1F0` / `sel+0x08` 两组（本仓库已实机验证，作为锚点）；
3. **钩子事件**：伤害钩子（ddh）在伤害事件里看到的**伤害来源 / 触发单位**，会作为已知单位补进账本，
   让没被选中过的单位也能被跟踪、结算。

单位显示**优先用名字**（解析不到退回 4 字符码）：名字按「JASS native `GetUnitName` → `0x326BA0` / `0x1DA520` → 退回码」三级降级解析。

「是不是一个单位」要几条同时成立才算（防误判）：

* 类型码 4 个字符全是字母/数字，且至少一个英文字母；
* 生命索引在界内，且 `表[索引]` 指向的对象可读；
* `0.05 < 最大HP < 1,000,000,000`；
* `-10,000 < 当前HP ≤ 最大HP × 1.01 + 1`；
* 头部 `+0x00` 的虚表落在 `game.dll` 映像内（只加分/降噪，不单独一票否决）。

「拥有者」字段是**运行时自发现**的：在单位头部找「唯一一个指向某个 `CPlayer*` 的字段」，
多个单位投票一致才采用（找不到就显示 `?`）。

**降噪（很重要）**：句柄表/钩子锚点也可能扫到「长得像」的内存。四道闸门：

1. **置信度**：生命链 +2、虚表在 game.dll +2、魔法索引可读 +1、坐标合理 +1、头部能找到 `CPlayer*` +1；
   低于门槛（默认 3）的候选直接丢。
2. **生命对象唯一**：真单位的“生命状态对象”是一人一个 —— 同一个生命对象被多个候选认领时，
   只留排名最高的那个（选区链 > 置信度高）。
3. **稳定性**：非选区链来源的新单位要**连续 3 轮**都被认出来才开始跟踪（闪一次的假候选进不来）。
4. **拥有者复核**：一旦自发现出拥有者字段偏移，就回头把「读不出拥有者」的非选区单位剔掉。

**生命表基址选择**也有验收门槛（踩过坑）：候选表必须真的“像表”，不能只凭“某一个真单位恰好能从它读出
一个可读指针”就认 —— 曾经因此把 `ctx+0x40` 上的垃圾认成生命表，全场单位判死。现在的规则是：
真单位命中 ≥2 个就算数；只命中 1 个时必须表本身也有像生命对象的项；一个都没命中时表打分要 ≥5。
而且**默认偏移（`ThisGame+0x0C`）优先**：只要它读得出来就用它，备选值只是它读不出来时的兜底。

### 生命表会在同一局里“搬家”（这一版修的就是它）

`ThisGame+0x0C` 在实机里一度显得“不稳定”：同一局里它会变成 `0x3E4C0010`、`0x34E90010`
这种地址，而软件报“未映射/不可读”，于是全场单位都判成“不像单位”。真相不是它抖，而是：

> **`IsReadable()` 查的是“attach 那一刻”的 VirtualQueryEx 快照。**
> 引擎在进图、扩容、回收时会**重新分配**生命表（搬到新内存，旧表释放掉），
> 这些新区域在快照里根本不存在 —— 明明 `ReadProcessMemory` 读得到，软件却说“未映射”。

于是真表被当成坏值丢掉，接着程序在垃圾里挑了一个“像表”的地址，全场单位判死。
（这也是为什么“先开游戏再开软件”常常正常，“刚进图就挂上”常常失败。）

现在的处理（`RemoteProcess.IsReadable`）：

1. 先查缓存的区域表（快，大多数命中走这条）；
2. 查不到 → **立刻重抓一次区域表**（节流 800ms），再查；
3. 还查不到 → **直接读 4 字节实测**（带每秒 2000 次的预算，防表基址探测被假地址拖慢）；
   读得到就算可读，并顺手把区域表补新。

外加：监视循环每 5 秒重抓一次区域表（不然引擎扩容后的新堆区永远看不见）。
同一局里表基址变了只会记一条日志 `生命表基址变更：… → …（账本保留）`；
判断“换图/重开局”改用 `(ctx, ThisGame)` 这两个整局不变的全局，不再拿表基址当判据 ——
否则表一搬家账本就被清空，死亡结算会莫名丢数据。

### 偏移是怎么确证的（静态 + 动态两条线）

* **静态**（直接读本机 `C:\3rd\war5\game.dll`，不用跑游戏）：
  * `GetUnitTypeId`（RVA 0x1E6670）= `call 0x1D1550`（句柄→CUnit*）→ `mov eax,[eax+0x30]` → `ret`
    ⇒ **CUnit+0x30 就是 4 字符类型码**；
  * `GetUnitName`（0x1E6340）走 `+0x30` → `0x326BA0` → `0x1DA520`（类型码→对象数据→字符串）；
  * 游戏内存表布局在 RVA 0x374CD3 处被引擎自己的代码确证：
    `mov eax,ds:[6FBE40A8]`（ThisGame）→ `cmp ecx,[eax+0x1C]`（容量上限）→ `mov eax,[eax+0x0C]`（表基址）
    → `cmp dword ptr [eax+ecx*8], 0FFFFFFFEh`（8 字节一项）。
    所以本软件也**照引擎的规矩**用 `ThisGame+0x1C` 卡索引上限（挡“凑巧像单位”的内存）。
* **动态**：`_test\fakegame\` 那个假魔兽（内存布局与外部可见的魔兽一致）跑端到端，
  验证单位跟踪、伤害事件与死亡结算。
* **实测**：真机跑一局即可确认（见下）。
内置版本表：War3Trainer 的 13 个版本（`1.20.4.6074` … `1.27.0.52240`），
当前游戏 `C:\3rd\war5`（1.27.0.52240）用最后一行。

## 8. 常见问题
* **提示需要管理员**：游戏是管理员权限跑的 → 右键 exe → 以管理员身份运行。
* **一直「还没发现单位」**：确认已经进地图；再点【生成诊断报告】，把 `logs\probe-*.txt` 发我
  （报告里有句柄表/选区链/内存表每一路的命中数，能立刻定位问题）。
  * 报告 §6 会写清楚“表基址到底是 **区域表里没有** 还是 **真的读不到**”
    （前者是区域表快照过期，这一版已会自动重抓 + 实测兜底）；
    §6.1 用真单位给每个候选表打分（单位命中 / 表打分），§6.2 直接把**引擎自己读表的那段代码**
    从内存里读出来，并把内存里的 `game.dll .text` 与磁盘文件逐字节比对 ——
    平台若在内存里改代码，一眼就能看见。
  * 如果连默认的生命表基址都对不上，报告 §6.1 会用真单位给每个候选表打分，帮助判断
    究竟是“还没进图”还是“这张图的表不在默认偏移”。
  * 日志里出现 `生命表基址变更：… → …（账本保留）` 是**正常的**：引擎在同一局里扩容/搬表了。
* **进程名不是 war3**：软件按 `war3 / game.dll / dzwar3 / Warcraft III / Frozen Throne` 找进程；
  你的平台如果用了别的名字，告诉我加进去。
* **CPU 占用高**：独立只读桌面模式可把 ini 里的 `interval_ms` 调大（例如 100~200）。
* **退游戏/换地图会不会刷一堆假结算**：不会。进程退出时直接断开、不结算；
  一次有 3 个以上单位同时消失（超过在场单位的一半）会被判为「地图结束/退游戏」，只丢账不出结算。
  当前 ddh 数据会保存在 SQLite；会话 ID 复用时仍可能出现旧数据混入，见 §0.3。
* **构建**：桌面程序通过 `DesktopHost` 项目构建，游戏内页面宿主已移除。
* **【伤害事件】页的「净掉血」为什么是 `?`**：这次事件没量到血 —— 目标已死（前血 ≤ 0）、
  生命表/状态对象读不到，或伤害函数入口/出口读血失败。`?` 表示“没测到”，不是 0 伤害。
* **为什么“地图伤害 > 0、净掉血 = 0”**：伤害发生了，但同帧回血、治疗、护盾或免伤抵消了血量差。
  地图伤害来自出口 `*out`，净掉血来自真实前后血差，两者不是同一个口径。
